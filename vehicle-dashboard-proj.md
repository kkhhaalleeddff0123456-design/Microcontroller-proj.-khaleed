## Executive Overview

This project presents the design and bare-metal software implementation of a real-time Digital Automotive Instrument Cluster based on the Microchip/Atmel ATmega32 8-bit AVR microcontroller. The system is engineered to capture, filter, process, and display critical vehicle telemetry parameters—including vehicle speed, engine RPM, fuel level, coolant temperature, battery voltage, and oil pressure—without reliance on an Real-Time Operating System (RTOS) or heavy floating-point libraries.

To operate efficiently within the memory and performance boundaries of an 8-bit architecture (32 KB Flash, 2 KB SRAM, 1 KB EEPROM), the software relies on register-level bitwise operations, fixed-point math conversions, hardware interrupts, and digital signal filtering routines. The result is a deterministic, low-latency cluster management system suitable for real-time automotive monitoring.

## Technical Subsystem Architecture

### 1. Speedometer & Odometer Module
* **Hardware Interface:** Configured via Timer1 Input Capture Unit (ICU) on pin `PD6 (ICP1)`.
* **Measurement Principle:** Measures the precise pulse period generated by a Vehicle Speed Sensor (VSS) attached to the transmission output shaft.
* **Speed Calculation:** Calculates vehicle speed within a range of 1 to 250 km/h using fixed-point integer arithmetic to prevent cycle-heavy floating-point calculations in the interrupt context.
* **Odometer & EEPROM Wear-Levelling:** Accumulated mileage is tracked in system RAM and periodically committed to the ATmega32 internal 1 KB EEPROM. To prevent premature EEPROM endurance failure (rated at 100,000 write cycles), a circular ring-buffer wear-levelling algorithm is implemented across dedicated memory blocks, rotating write addresses alongside a status header.

### 2. Tachometer (Engine RPM Processing)
* **Hardware Interface:** Configured using External Interrupt 0 (`INT0`) on pin `PD2`.
* **Measurement Principle:** Detects falling-edge pulses originating from the engine ignition coil or crankshaft position sensor interface.
* **Sampling Window:** Uses a dedicated 250 ms time-base derived from Timer0 overflow interrupts. Every 250 ms, the captured pulse count is evaluated, scaled to RPM ($RPM = \text{pulses} \times 240 / \text{pulses\_per\_rev}$), and reset for the next sampling cycle. Software window filtering eliminates transient ignition noise and contact bounce.

### 3. Analog Gauge Acquisition & Signal Filtering
* **Hardware Interface:** 10-bit Successive Approximation ADC running in single-ended mode across PORTA (`PA0` to `PA3`).
* **Monitored Parameters:**
  * Fuel Tank Level (`PA0`)
  * Engine Coolant Temperature (`PA1`)
  * Vehicle System Battery Voltage (`PA2`)
  * Engine Oil Pressure Switch/Sensor (`PA3`)
* **Filtering Pipeline:** Raw analog inputs from vehicle sensors suffer from electrical noise, engine vibration, and fuel sloshing. To yield stable readings on the display, inputs pass through a hybrid digital filter:
  1. **Median Filter (5 samples):** Rejects high-amplitude, short-duration voltage spikes.
  2. **Moving Average Filter:** Smooths step transitions over a sliding sample window before passing data to the display logic.

### 4. Ignition State Machine (FSM)
System operation is governed by a deterministic Finite State Machine handling power modes, pre-start checks, and fault responses:

```text
[OFF] ----(Key Insert/ACC)----> [ACC] ----(Key On)----> [IGNITION]
                                                           |
                                                  (Self-Test Start)
                                                           v
[LIMP HOME] <---(Critical Fault)--- [RUNNING] <---(Engine Start)--- [BULB CHECK]

OFF State: Minimum peripheral power consumption; background wake-up monitors active.
ACC State: Powers basic infotainment/accessory buses and renders display splash diagnostics.
IGNITION State: Energizes sensor arrays and initiates main system initialization routines.
BULB CHECK State: Runs a mandatory 2-second pre-flight self-test. Illuminates all warning LEDs and sounds the audio chime to verify lamp integrity before engine cranking.
RUNNING State: Primary operational state. Continuously executes sensor sampling, display refresh, and alert monitoring loops.
LIMP HOME State: Fallback state triggered upon critical hardware thresholds (e.g., severe coolant overheat or zero oil pressure). Disables non-essential routines, limits refresh rates, and locks high-priority visual/audible alarms.

5. Shift Register & Warning Lamp Array
Hardware Interface: Hardware SPI (PB4/SS, PB5/MOSI, PB7/SCK) driving an external 74HC595 8-bit Shift Register.
Pin Efficiency: Expands the ATmega32 I/O capabilities by driving 8 dedicated automotive warning lamps (Check Engine, Oil Pressure, Low Fuel, Battery Fault, High Beam, Turn Signals, Coolant Overheat, Brake System) using only 3 MCU pins.
Audio Alerts: A piezo sounder driven by Timer2 PWM outputs distinct tone frequencies and pulse patterns matching active warning priority levels.

6. Diagnostic Serial Telemetry (USART)
Hardware Interface: Hardware USART (PE0/RXD, PE1/TXD) configured at 9600 baud, 8 data bits, 1 stop bit, no parity (8N1).
Broadcast Cycle: Transmits a structured diagnostic telemetry frame every 5,000 ms to an external telemetry logger or OBD diagnostic tool.
Frame Structure:
[START_BYTE (0xAA) | SPEED_BYTE | RPM_HIGH | RPM_LOW | FUEL_PCT | TEMP_C | VOLT_x10 | STATUS_FLAGS | CHECKSUM]

Codebase Architecture
The project follows a strict four-layer architecture, enforcing modularity and clean separation between hardware-dependent register code and application logic.
Cluster_Project/
├── Service/                        # Services & Core Utilities
│   ├── STD_Types.h                 # Standard type definitions (u8, u16, u32, s8, etc.)
│   └── Bit_Math.h                  # Bitwise macro definitions (SET_BIT, CLR_BIT, etc.)
│
├── MCL/                            # Microcontroller Abstraction Layer (MCAL)
│   ├── DIO/                        # Digital Input/Output register operations
│   ├── ADC/                        # ADC configuration, channel select, and conversion
│   ├── TIMER/                      # Timer0, Timer1 (ICU), and Timer2 drivers
│   ├── EXTI/                       # External Interrupt configuration (INT0, INT1)
│   ├── SPI/                        # Hardware SPI master driver
│   ├── UART/                       # Serial communication driver
│   └── EEPROM/                     # Internal EEPROM read/write routines
│
├── HAL/                            # Hardware Abstraction Layer (Board Components)
│   ├── LCD/                        # Character LCD driver (HD44780 interface)
│   ├── Keypad/                     # Input switch array processing
│   ├── SevenSegment/               # Display multiplexing driver
│   └── ShiftRegister/              # 74HC595 shift register control functions
│
└── src/                            # Application Layer
    ├── FSM.c / FSM.h               # Ignition state control & alert threshold logic
    └── main.c                      # Application entry point & main scheduling loop

Module Layering Responsibilities

Service Layer: Ensures portable data types and fast bitwise register access across all drivers.

MCL Layer: Handles direct memory-mapped register configuration for the ATmega32 internal peripherals.

HAL Layer: Abstracts external hardware modules from MCU pin specifics, providing high-level APIs to the application.

Application Layer (src/): Implements system business logic, state transitions, signal filtering algorithms, and main scheduling loop without direct register manipulation.

## Proposed Testing & Simulation Plan (Proteus VSM)

To validate the system architecture and logic before physical implementation, the cluster will be tested in Proteus VSM according to the following plan:

* **Frequency Input Testing:** Signal generators connected to `PD6 (ICP1)` and `PD2 (INT0)` will inject square waves (10 Hz to 2.5 kHz) to verify linear scaling for Speedometer and Tachometer logic.
* **Analog Filtering Verification:** Potentiometers with introduced voltage noise will be used on ADC channels (`PA0-PA3`) to verify that the proposed median and moving average filters smooth out sensor fluctuations.
* **Shift Register Bus Analysis:** A virtual logic analyzer will monitor `PB4`, `PB5`, and `PB7` to confirm correct SPI timing and latch pulse generation for the 74HC595 warning lamp array.
* **Serial Telemetry Logging:** A Virtual Terminal connected to `PD1 (TXD)` will parse outgoing 9600-baud diagnostic telemetry frames to ensure frame structure and checksum accuracy.

## Anticipated Design Constraints

* **Maximum Input Frequency:** High-speed pulse capturing via interrupts is limited near 10 kHz to prevent excessive interrupt overhead on the 16 MHz AVR core.
* **Shared SPI Bus Timing:** Driving the 74HC595 shift register requires dedicated latch control to prevent visual LED flicker during multi-byte SPI transfers.
* **ADC Latency:** Sequential channel conversions across 4 analog inputs will be implemented using non-blocking interrupt-driven ADC sampling to prevent main loop stalling.
